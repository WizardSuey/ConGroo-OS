# Протокол работы: ученик ↔ учитель (Cursor)

Этот документ — контракт. Код пишешь **только ты**. Учитель не присылает готовое ядро и не делает за тебя коммиты с реализацией (кроме правок учебных docs по договорённости).

---

## Роли

### Ученик / Operator (ты)
- Пишешь код, lab notes, схемы в этом репозитории через **Cursor**.
- Сам запускаешь сборку и QEMU (каждая попытка — runline).
- Сдаёшь работу **сообщением в чат агента** + файлами в git.
- Честно помечаешь, что не понял / что скопировал из гайда (если смотрел — укажи источник).
- Держишь вайб лаборатории без прямых аниме-отсылок (см. [`PHILOSOPHY.md`](PHILOSOPHY.md)).

### Учитель (агент в Cursor)
- Даёт теорию модуля, чеклист, наводящие вопросы.
- Проверяет сдачу по критериям модуля и на **конгруэнтность** понимания.
- Указывает ошибки, пробелы в модели, следующий эксперимент.
- Может показать **фрагмент-эталон на 5–15 строк** только после твоей попытки и только как разбор идеи — не как «вставь и забудь».
- Не пишет за тебя целые файлы ядра/драйверов/планировщика.

```text
congrou/                 # (появится) исходники ОС — пишешь ты
```

Имя каталога с кодом: **`congrou/`** (создашь на Модуле 1).

## Как сдавать работу

### 1. Одна сдача = один модуль или одна чёткая подзадача

Не смешивай «чуть памяти» и «чуть прерываний» в одной сдаче без пометки.

### 2. Перед сдачей

1. Обнови код/заметки в репозитории.
2. Заполни шаблон [`templates/SUBMISSION.md`](templates/SUBMISSION.md) → сохрани как:

   ```text
   docs/submissions/M0X-YY-short-name.md
   ```

   Пример: `docs/submissions/M00-01-boot-map.md`

3. Закоммить **в `main`** (рабочая ветка курса — всегда `main`):

   ```bash
   git checkout main
   git add -A
   git commit -m "submit(M00): boot map and terms"
   git push origin main
   ```

4. В чате Cursor напиши коротко:

   ```text
   СДАЧА: M00 / задача A–D
   Файл: docs/submissions/M00-01-boot-map.md
   Что проверить: схема загрузки + термины
   Что не уверен: linker script, rings
   ```

### 3. Обязательные поля сдачи

- ID модуля и название задачи
- Что сделано (список)
- Как проверить (команды: `make`, `qemu-system-x86_64 ...`)
- Ожидаемый результат (что должно появиться в serial/экране)
- Самопроверка по чеклисту модуля (да/нет)
- Вопросы учителю (если есть)
- Источники (книги/сайты/видео), если пользовался

### 4. Для код-модулей — ещё

- Дерево ключевых файлов (кратко)
- Известные баги / TODO
- Скрин/копия вывода QEMU (текст лога достаточно)

## Как учитель проверяет

Проверка идёт в **три слоя**.

### Слой A — Форма (быстро)
- Есть файл сдачи и понятные команды запуска
- Сдача относится к текущему модулю
- Нет «магических» бинарников без исходников

### Слой B — Критерии модуля
- Сверка с `Acceptance criteria` в карточке модуля
- Для теории: точность определений, связность схемы
- Для кода: boot/сборка, поведение в QEMU, отсутствие явного UB в критичных местах

### Слой C — Понимание (главное)
Учитель задаёт 2–5 вопросов вида:
- «Почему linker script обязателен?»
- «Что будет, если забыть `cli` здесь?»
- «Кто владеет этой страницей памяти?»

Если ответы слабые — модуль **не закрывается**, даже если «как-то работает».  
ConGroo учит модели машины, а не зелёной галочке.

---

## Вердикты проверки

| Вердикт | Значение | Что дальше |
|---------|----------|------------|
| **PASS** | Модуль/задача закрыты | Можно брать следующий блок |
| **PASS WITH NOTES** | Суть ок, есть замечания | Исправить по списку, можно параллельно идти дальше |
| **REWORK** | Не хватает критериев или понимания | Доработка по пунктам, повторная сдача |
| **BLOCKED** | Мешает окружение/инструменты | Учитель помогает разблокировать setup |

Формат ответа учителя в чате:

```text
ВЕРДИКТ: REWORK
Слой A: ok
Слой B: не хватает ...
Слой C: вопросы ...
Что сделать до следующей сдачи:
1. ...
2. ...
```

## Ритм занятий в Cursor

Рекомендуемый цикл (один «ход»):

1. Учитель открывает/уточняет подзадачу модуля.
2. Ты работаешь в редакторе (код + заметки).
3. Ты сдаёшь по протоколу.
4. Учитель проверяет и даёт вердикт + теорию на следующий шаг.

Можно сдавать **частично** внутри модуля (`M03-part2-idt`).  
Нельзя просить «напиши мне ISR целиком» до своей попытки.

## Правила про подсказки и «spoilers»

| Можно просить | Нельзя ожидать |
|---------------|----------------|
| Объяснить концепт ещё раз | Готовый драйвер/планировщик |
| Наводящий вопрос / где искать баг | Полный diff «вот правильный файл» |
| Разбор *твоего* кода построчно | Решение домашки до попытки |
| Эталон *после* REWORK, крошечный | Списать модуль из блога без понимания |

Если застрял > 45–60 минут на одной ошибке:
1. Опиши симптом, что уже пробовал, релевантный код.
2. Учитель даёт **гипотезы и порядок проверки**, не готовый патч.

## Git-дисциплина (простая)

- Рабочая ветка курса: **только `main`** (feature-ветки не используем)
- Коммиты осмысленные: `feat(mm): bump frame allocator`, `submit(M02): printk`
- Не коммить артефакты: `*.o`, `*.elf`, `iso/`, логи — в `.gitignore`
- Одна логическая идея ≈ один коммит (идеал, не догма)
- Учитель тоже пишет учебные правки docs сразу в `main`

---

## Обновление прогресса

После **PASS** / **PASS WITH NOTES**:
1. Ученик или учитель обновляет [`PROGRESS.md`](PROGRESS.md).
2. Статус модуля: `not_started` → `in_progress` → `done`.

---

## Анти-паттерны

- Сдача без команд запуска
- «Оно работает» без объяснения, *почему*
- Копипаст large chunks из OSDev без пометки источника
- Прыжок через модули («сразу paging»), пока не закрыт фундамент
- Просьба учителю «просто сделай, чтобы бутнулось»
